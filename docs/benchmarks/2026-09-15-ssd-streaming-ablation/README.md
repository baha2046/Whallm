# SSD 串流六項實驗：本機 V4 與 Qwen

2026-09-15，M5 Pro、64 GiB、MLX 0.32.2。這是目前工作樹的獨立研究測試，
不是 App 的新預設，也不是所有輸入都適用的速度保證。
六項研究均已得到本輪結論：最一致的正向訊號來自 V4 的 Prefill 直接讀取；
其餘結果與限制分列如下。沒有修改 App 預設。

## 比較方法

- 程式起點：`6cdbdce2fba0085c035c982be1d18bfc7387f3bf`，另保存每輪研究程式與 runtime 的內容雜湊和副本。
- V4 是本機 DeepSeek V4 Flash 0731，43 層；Qwen 是 Qwen3.8 Flash Next，48 層。
  沒有測 V4.1。
- 普通生成基準固定 LRU：V4 1152 slots、Qwen 3072 slots。
  greedy、相同輸入與輸出長度，Prompt Cache 關閉，每次新程序，初始 expert slots 為空。
  表內 request／首次回覆時間從請求開始計算，不包含最初載入模型的時間；程序總時間另存原始紀錄。
- 先測 code 1K／64 tokens，正向訊號再以繁中技術題 4K／128 tokens 檢查。
  第 6 項先用 code 1K／32 tokens 檢查完整生成。
- 每組兩輪，第二輪倒序。標有 `prime` 的組別在每個計時程序前執行相同的原版請求。
  系統檔案快取未清空，不能稱為冷 SSD 或快取完全相同的比較。
- 表內變化為各輪「候選 ÷ 同輪原版 − 1」的中位數。時間負值代表縮短，速度正值代表提高。
  僅兩對樣本，範圍是觀察值範圍，不是信賴區間。
- 輸出 token 完全一致、沒有新增 swapout、額外記憶體不超過 1 GB，才通過本輪採用前檢查。
  初篩只記錄 MLX peak；後續同時記錄程序 RSS peak。
  改善 5% 是延伸測試門檻，不代表已證明普遍有效。

## 1. 每層統計

已增加獨立 observer，輸出每層命中率、每 token 未命中數、讀取資料量、
讀取工作累計時間與前景取得權重的時間。observer 的耗時不拿來比較加速。

1K code、128 output tokens 的觀察：

| 模型 | 各層命中率範圍 | 全模型 misses/token | 全模型讀取 GB/token |
| --- | ---: | ---: | ---: |
| V4 | 23.75–71.92% | 106.83 | 1.428 |
| Qwen | 39.13–83.46% | 153.83 | 0.402 |

兩模型逐層讀取量加總均與 runtime 計數一致。第一個輸出來自 Prefill，
因此 128 output tokens 對應 127 次 Decode route。
GB 使用十進位；這是程式要求的專家資料量，可能由 OS cache 提供，並非 SSD 實際流量。

**尚未取得可歸因的 GPU 等待 I/O 時間。** 目前前景時間也包含 CPU 工作，
多個讀取工作可同時進行，兩者都不能冒充 GPU idle。該欄位保留 `null`。
這項是量測工具，不填寫生成速度改善百分比。

另外完成 Qwen 1K／8-token 的原生 Metal System Trace，目標程序正常結束，
匯出 9,174 個目標程序 GPU 活動區間。現有標記是 command buffer，沒有模型層與
同步的 I/O 區間，仍不足以把 GPU 空檔歸因到每層讀取。
見 [GPU 紀錄檢查](qwen-gpu-summary.json)；完整 `.trace` 保留在 scratch，
只將目標程序的區間 CSV 放入原始證據封存。

## 2. 動態分配與路由熱門度

原快取本來就跨層共用。先單獨移除每層最低保留量，再測 LFU、每約 16 tokens
衰減的熱門度，以及「熱門度 × 該層過去平均讀取成本」；總 slots 不變。

實作範圍：使用次數保存在常駐的 `_Entry` 中，專家被淘汰時一併移除；重新載入時
不會恢復過去的熱門度。因此本輪測的是常駐項目的頻率／成本加權淘汰策略，
尚未實作跨淘汰保留的全專家路由統計、分開的長短期熱門度，或按逐層快取效益
調整配額的策略。不能把本輪結果當成完整「路由感知快取」已測完或無效的結論。

V4 1K 初篩 LFU 生成速度 +10.91%；4K 繁中延伸為 **+5.24%**，
兩輪分別 +1.75%／+8.74%，整次請求縮短 3.86%。這是值得保留的訊號，但幅度不穩定。
熱門度版本 4K 只有 +3.51%；成本加權版本只有 +0.44%，且讀取量增加 29.63%。
Qwen 的四個基礎版本都不到 1% 生成速度改善；成本加權反而慢 5.74%、讀取量增加 26.18%。

結論：本輪這幾個淘汰策略沒有跨模型的穩定收益。V4 LFU 可保留為明確條件下的候選；
完整的全專家路由感知快取尚未測試。

後續更新：使用者另要求完整功能，已另外實作
[路由感知快取](../../ROUTE_AWARE_CACHE.md)。本節數字及「尚未」描述保留本輪測量當時的範圍。

## 3. Prefill／Decode 分開讀取

Prefill 使用獨立的檔案描述符，關閉檔案快取與預讀；Decode 使用普通 cached reader。
先測對齊暫存再複製，接著測直接讀進 GPU 可用記憶體。

V4 直接讀取版本：1K code／128 tokens 的首次回覆時間縮短 10.93%，
4K 繁中縮短 **14.65%**（兩輪 14.25–15.05%），整次請求縮短 **6.35%**。
但 4K 生成速度平均下降 3.36%，所以收益主要在輸入處理。

Qwen 暫存複製版本：4K 整次請求縮短 3.12%，生成速度 +8.33%。
短輸入曾出現較大的改善，但原版前後速度差很多，不能直接採信短測試的最高百分比。
Qwen 再改成每層兩次連續讀取，24,576 個專家全部直接讀入、沒有暫存複製：
保留系統快取的版本 request 僅縮短 0.47%。繞過 Prefill 快取的版本其中一輪
出現 16 pages（約 0.25 MB）系統 swapout，該輪不採為有效效能證據；
另一輪 request 縮短 3.41%、首次回覆縮短 5.44%，但只剩一對有效樣本。
因此本輪沒有足夠證據採用 Qwen 連續讀取版本。所有輸出 token 仍一致。

## 4. 自適應部分／整層讀取

保留原有計算，等路由確定後只載入需要的專家，密度超過 80% 時改讀整層。
Qwen 同一層各批次共用已載入的資料。

V4 1K：讀取量少 11.69%，整次請求卻增加 **21.41%**，首次回覆增加 31.61%。
Qwen 1K：整次請求縮短 6.31%；換成 4K 繁中後增加 **6.34%**，
即使讀取量仍少 5.65%。本輪不採用這兩個版本。

少讀資料沒有直接換成加速；延後到路由確定才讀，可能抵銷既有預讀與計算重疊。
這是對結果的解釋假設，沒有獨立 GPU trace 證明其占比。

## 5. 共啟用專家重新排列

以前半段 route 學排列，後半段實際 misses 評估；沒有用待測資料訓練。
實作獨立權重副本與連續區段讀取，在固定第 12、32 層比較。
所有被讀取的專家 bytes 均和原檔相同；不覆寫已安裝模型。

離線估計可少 6.84%（V4）／10.46%（Qwen）讀取呼叫。
但真權重 bypass 測試，相對「原 ID 排列＋合併連續區段」：

| 模型 | 第 12 層時間變化 | 第 32 層時間變化 |
| --- | ---: | ---: |
| V4 | +2.73% | −0.31% |
| Qwen | +1.20% | +2.15% |

warm 測試也沒有超過 5% 的改善。bypass 共 24 個測量起點的檔案 resident bytes 為 0。
Qwen 有個首次逐專家讀取樣本偏慢，不能把相對該樣本的約 43% 差距歸功於排列。
結論：在 component 檢查停止，未整合全模型排列，**沒有全模型生成加速百分比**。

## 6. DSpark／MTP、路由預讀與專家聯集

逐 token 驗證、聯集驗證、聯集預讀各自比較。
固定 expert 預算：V4 主模型 948＋DSpark 96＋預讀最多 108 slots；
Qwen 主模型 2980＋MTP 32＋預讀最多 60 slots。
另測 V4 1152 main＋768 DSpark 的較大快取版本，分開報告記憶體代價。

Qwen code 1K／32 的兩輪全部輸出一致、沒有新增 swapout：

| Qwen 版本 | 整次請求時間 | 生成速度 |
| --- | ---: | ---: |
| 逐 token 驗證 | +9.88% | −14.41% |
| 聯集驗證 | +8.41% | −4.00% |
| 聯集預讀 | +8.62% | −6.95% |

三種版本都在第一輪接受 0 個候選，隨即使用既有 fallback 回普通生成。
因此這組測到的是「一次失敗嘗試＋普通生成」，不是持續接受候選的吞吐能力。
聯集驗證比逐 token 驗證省時，但沒有比普通生成快；預讀還增加主模型讀取量。
V4 四個版本、兩輪的輸出彼此一致，但都從第 24 個 token 起與普通生成不同：
原版 `for a Mixture`，DSpark `for Mixture`。即使逐 token 驗證與較大草稿快取也相同。
因此 **V4 第 6 項未通過本輪的輸出一致檢查，不提供有效加速百分比**。
原始耗時仍保存，不能拿不同輸出序列當成同工作量比較。

固定預算的聯集預讀 MLX peak 約比原版多 1.29 GB，較大草稿快取版本多 5.68 GB，
也超過預設的 +1 GB 條件。兩輪皆沒有新增 swapout。
補測普通生成關閉整層 Prefill、以及 DSpark 信心門檻設為 1（實際提出 0 tokens），
兩者都得到和四個 DSpark 版本相同的完整 token hash。
這把差異縮小到既有 Prefill／主模型執行路徑，不能把它歸因於聯集預讀；
尚未定位是哪個中間張量或數值捨入造成差異，也不能宣稱 DSpark 接受／回退邏輯已全面驗證。

另外以相同輸出的 DSpark 逐 token 驗證為基準，兩輪完整請求比較如下：

| V4 版本 | 請求時間變化 | 主模型＋草稿讀取量 | 額外 MLX peak |
| --- | ---: | ---: | ---: |
| 聯集驗證 | +1.15% | −2.04% | 約 −1 MB |
| 聯集預讀 | +0.89% | −2.43% | +1.44 GB |
| 較大草稿快取＋聯集預讀 | +1.62% | −4.61% | +5.83 GB |

即使改用此相同輸出的對照，仍沒有測到請求加速。草稿接受率約 80.95%，
說明高接受率本身不足以保證 SSD 串流推測生成較快。

# 路由感知快取

2026-09-15 的工作目錄新增完整 `route` 專家快取策略。
它記住所有專家的使用紀錄，即使權重已被淘汰，也不會丟掉歷史；
再依預期能省下的讀取成本，調整各層的快取容量。

## 啟用

App：模型進階設定 → Expert cache eviction → **路由感知**。
CLI 與獨立 Server：`--expert-eviction-policy route`。
Catalog：該模型 `runtime.expert_eviction_policy` 設為 `"route"`。
變更設定後重新載入模型生效。

App 的既有 LRU 預設、CLI／舊 catalog 的 LFU 預設不變。
舊偏好仍可讀取；新 App 偏好 `routeAwareExpertCache` 缺省或 false 時，
沿用 `recentExpertCache` 的選擇。總 Slots、權重格式和安裝檔案不變。
目前是原始碼功能；尚未重新封裝或發布 App。

## 如何保留權重

| 部分 | 行為 |
| --- | --- |
| 全專家歷史 | 固定大小的陣列記錄每層每位專家，與常駐權重分開 |
| 短期熱門度 | 半衰期 16 個該層觀察到的 token，較快跟上主題變化 |
| 長期熱門度 | 半衰期 256 個該層觀察到的 token，保留較長時間的偏好 |
| 輸入處理 Prefill | 每個請求另計使用頻率，提供較弱的初始參考，不灌入 Decode 歷史 |
| 讀取成本 | 用實際完整專家讀取時間的平滑值；分段讀取加總兩段實際耗時 |
| 各層容量 | 約每 16 個完整 Decode tokens 重算，把下一個槽位給預期收益最高的層 |
| 淘汰 | 優先從超出目標容量的層淘汰低分專家；同分時淘汰較久未用的專家 |

分數為 `(0.75 × 短期 + 0.25 × 長期 + 輸入參考) × 相對讀取成本`。
輸入參考權重起始為 0.1，隨本請求 Decode 以 32-token 半衰期下降。
讀取成本相對於已觀察層的中位數，限制在 0.5–2 倍；未知層使用中位數。
這是可驗證的啟發式估計，並非知道未來路由的最佳分配。

各層目標容量加總不超過 Slots。目標是軟限制：當次需要的專家和其他仍被使用中的
專家必須保留，不能為了達到配額而覆寫仍在使用的權重。
沒有可淘汰槽位時沿用既有失敗／清理機制。每層只檢查最弱的可淘汰候選，
定期清理過期候選，不會讓歷史隨請求數無限增長。

這項策略改變保留哪些權重，不改路由器選擇、權重內容或模型計算。
需要的專家仍會載入既有槽位；不包含預測讀取、跳過專家或磁碟重新排列。

## 生命週期與觀測

- 歷史存活到模型卸載。同一已載入模型的後續請求會沿用長短期歷史；不存磁碟。
- 每個請求只重設一次 Prefill 統計，按層處理和最後一個輸入 token 會合併計算。
- Prefill 釋放權重槽位時保留歷史。取消、讀取失敗後仍保留已觀察到的使用紀錄。
- 推測生成的驗證與重播路由也算觀察，不限於最後接受的輸出 tokens。
  MTP／DSpark 的主模型與草稿快取各自保留歷史與容量。
- Prefill 階段沿用生成器的首次回傳邊界，可能包含它提前計算的少量 Decode 工作。
- V4 原有的按層 Prefill 會略過最後一層 FFN，只建立該層 KV 狀態。
  因此這層沒有整段輸入的專家路由；本輪統計只有首次回傳前實際計算的 2 個位置。
- 一般路徑計算完整 top-k 選擇的重複次數。只有專家聯集的外部呼叫無法重建
  原始 token 次序與重複次數，不能用它當成精確的逐 token 統計。

CLI 的 `--metrics-json` 新增 `route_cache`；非 route 策略為 null。
包含半衰期、重分配次數、歷史範圍、陣列占用，以及每層的目標／實際槽位、
觀察 token 數、有歷史的專家數、讀取時間樣本及預估保留價值。
`metadata_array_bytes` 只計 NumPy 陣列，不能當成整個快取的記憶體占用。

## 驗證與限制

功能測試涵蓋淘汰後保留歷史、主題轉移、輸入隔離、兩段 Prefill 合併、
層間容量轉移、槽位唯一性、權重 bytes、分段讀取、pinning、失敗重試與取消清理。
CLI／catalog 和 App 偏好相容性亦有測試。

以下是分開 Prefill 讀取預設啟用之前的測量，尚未量測兩項功能合併後的收益。
當時 Python 440 項、Swift 設定測試 31 項通過。16 次計時生成的輸出一致、無新增換頁。
V4／Qwen 的連續請求、換題、生成中取消、釋放槽位後重試也全部通過，
核對各次輸出的前 32 tokens，並確認跨請求歷史和 Prefill 重設行為。
本機 1K 的 V4／Qwen 完整請求時間分別縮短 10.54%／9.87%；
4K 的完整等待時間接近持平，未證明有穩定的長輸入收益。
詳見 [效能報告與原始證據](benchmarks/2026-09-15-route-aware-cache/README.md)。

完整模型測量：V4、Qwen；V4.1 共用路徑及設定已接入，完整 checkpoint 未安裝，
不宣稱已完成其生成或效能驗證。新策略可手動選擇；速度會受模型、輸入、
Slots 與作業系統檔案快取影響，不保證比 LRU 快。
